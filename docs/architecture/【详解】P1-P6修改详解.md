# P1-P6 修改详解

## 目标

这份文档解释 RepoPilot 后续 P1-P6 改造路线里的专业术语、为什么要这么改、改完有什么收益、具体要改哪些代码，以及如何通过测试产出可写进简历的数据。

核心原则是：不要盲目复制 DeepSeek Harness 或 Alibaba OpenCodeReview，而是把它们最有工程价值的机制做成 RepoPilot 能承受的轻量版本。

## 总览

| 优先级 | 改造主题 | 一句话解释 | 主要收益 |
| --- | --- | --- | --- |
| P1 | 工具结构化与 transcript snapshot | 把工具调用/结果从文本约定升级为结构化协议，并固定模型可见行为快照 | 降低工具解析脆弱性，提升可测试性 |
| P2 | Session Event Log | 用 append-only 事件日志作为会话权威来源 | 恢复、回放、审计更可靠 |
| P3 | 轻量规则系统 | 按文件路径/类型注入项目规则 | 减少无关上下文，提高任务约束稳定性 |
| P4 | Coverage Manifest | 把一次 agent run 覆盖了什么、验证了什么、失败了什么结构化输出 | 让 agent 行为可审计、可量化 |
| P5 | Review/Inspect 专用模式 | 借鉴 OCR 的确定性文件选择 + structured finding | 大变更分析更稳定，适合做简历亮点 |
| P6 | 上下文压缩实验 | 对比当前 section clipping 和三分区 tool-round compression | 用数据证明 memory/context 策略有效 |

## P1：工具结构化与 Transcript Snapshot

> 一句话概括：【原先的通过字符串约定来提取数据，改为用对象/结构体，字符串只作为渲染结果】

### 专业术语

**Tool Protocol（工具协议）**  
模型如何表达“我要调用哪个工具、传什么参数”，以及 runtime 如何把工具结果返回给模型。

RepoPilot 当前工具协议是文本形式：

```xml
<tool>{"name":"read_file","args":{"path":"README.md"}}</tool>
```

或者：

```xml
<tool name="patch_file" path="a.py">
  <old_text>...</old_text>
  <new_text>...</new_text>
</tool>
```

这能跑，但本质上是“模型输出文本，runtime 再解析文本”。

**Schema-first Tools（schema 优先工具）**  
先定义工具的参数 schema、输出 schema、风险等级、执行函数，再由这些定义生成 prompt 里的工具说明、参数校验和测试断言。

**Structured Result（结构化结果）**  
工具结果不只是字符串，而是对象。例如：

```json
{
  "status": "error",
  "error_code": "tool_failed",
  "value": {
    "exit_code": 1,
    "stdout": "",
    "stderr": "pytest failed"
  },
  "rendered_text": "exit_code: 1\nstdout:\n(empty)\nstderr:\npytest failed"
}
```

模型仍然可以看到 `rendered_text`，但测试和 report 可以读取 `value`、`status`、`error_code`。

**Transcript Snapshot（对话快照测试）**  
固定一次模型可见的完整 transcript，包括 prompt、tool call、tool result、final answer。以后 prompt 或工具协议变化时，snapshot 会显示差异。

### 为什么要改

RepoPilot 当前最大的问题之一是工具边界偏脆弱：

- `run_shell` 的成功失败靠字符串里的 `exit_code:` 正则判断。
- 工具参数 schema 是给模型看的字符串，不是真正统一的校验来源。
- 工具结果既给模型看，又给 report/trace 用，职责混在一起。
- 如果以后接 provider-native tool calling，需要重新设计协议。

DeepSeek Harness 和 Alibaba OCR 都说明了一个趋势：生产级 agent 不会长期依赖自然语言工具协议，而会走结构化 tool call 和 structured output。

### 改完有什么好处

1. **工具失败更可解释**  
   失败原因可以稳定分类为 `invalid_arguments`、`tool_failed`、`approval_denied`、`path_escape` 等。

2. **测试更容易写**  
   测试不用解析字符串，可以直接断言 `ToolResult.status == "error"`。

3. **后续接原生工具调用更容易**  
   OpenAI/Anthropic/DeepSeek 的 native tool calling 都依赖 schema。RepoPilot 如果内部已经 schema-first，外层 transport 可以替换。

4. **简历表达更专业**  
   你可以说“我实现了 schema-first tool protocol 和 structured tool result”，而不是“我用字符串解析工具调用”。

### 需要改哪些代码

主要涉及：

- `repopilot/tools.py`
- `repopilot/tool_executor.py`
- `repopilot/runtime.py`
- `repopilot/prompt_prefix.py`
- `tests/test_tools.py`
- `tests/test_tool_executor.py`
- `tests/test_agent_loop.py`

建议新增：

- `repopilot/tool_protocol.py`
- `tests/test_tool_protocol.py`
- `tests/snapshots/`

### 具体怎么改

第一步：新增核心 dataclass。

```python
@dataclass(frozen=True)
class ToolDefinition:
    name: str
    description: str
    args_schema: dict
    risky: bool
    execute: Callable[[dict], "ToolResult"]

@dataclass(frozen=True)
class ToolCall:
    name: str
    args: dict
    call_id: str = ""

@dataclass(frozen=True)
class ToolResult:
    status: str
    value: dict | str | list | None
    rendered_text: str
    error_code: str = ""
    metadata: dict = field(default_factory=dict)
```

第二步：让 `tools.py` 的工具函数返回 `ToolResult`，不是裸字符串。

例如 `run_shell`：

```python
return ToolResult(
    status="ok" if result.returncode == 0 else "error",
    error_code="" if result.returncode == 0 else "tool_failed",
    value={
        "exit_code": result.returncode,
        "stdout": result.stdout,
        "stderr": result.stderr,
        "timeout": False,
    },
    rendered_text=render_shell_result(...),
)
```

第三步：`ToolExecutor` 不再从 content 里正则提取 `exit_code`。

当前逻辑类似：

```python
match = re.search(r"exit_code:\s*(-?\d+)", content)
```

改成：

```python
exit_code = tool_result.value.get("exit_code")
```

第四步：`prompt_prefix.py` 从 `ToolDefinition.args_schema` 自动渲染工具说明。

第五步：新增 transcript snapshot。

可以先做轻量版：跑 FakeModel，记录：

- prompt metadata。
- 模型原始输出。
- parsed tool call。
- tool result structured value。
- final answer。

### 怎么测试

新增测试：

- 缺参数会返回 `invalid_arguments`。
- path escape 会返回 `path_escape`。
- shell 非零退出会返回 `status="error"`。
- patch 多处匹配会返回明确错误。
- snapshot 能固定一次完整 tool loop。

可量化指标：

- malformed tool recovery pass rate。
- tool error classification accuracy。
- snapshot case count。

### 面试怎么说

> 我把 RepoPilot 的工具层从文本解析升级为 schema-first tool protocol。工具调用、参数校验、执行结果和模型可见文本被拆开，工具返回 structured result，report 和测试可以直接读取状态码、错误码和结构化 value。这样既降低了模型输出格式漂移带来的脆弱性，也为后续接 provider-native tool calling 做了准备。

## P2：Session Event Log

> 

### 专业术语

**Session（会话）**  
一次持续交互的状态，包括用户消息、assistant 消息、工具调用、工具结果、memory、checkpoint。

**Event Log（事件日志）**  
把会话中发生的事实按时间追加写入，而不是只保存最终状态。

例如：

```json
{"type":"user_message","seq":1,"data":{"content":"fix tests"}}
{"type":"tool_call","seq":2,"data":{"name":"read_file","args":{"path":"test.py"}}}
{"type":"tool_result","seq":3,"data":{"status":"ok","value":{...}}}
```

**Append-only（只追加）**  
事件只新增，不原地修改旧事件。这样更容易审计和恢复。

**Projection（投影）**  
从事件日志重新计算出当前状态。例如从 events 投影出 history、memory、report。

### 为什么要改

RepoPilot 当前状态有几份：

- session JSON。
- run trace。
- report。
- checkpoint。
- memory。

这些都有用，但不是同一个权威来源。恢复时需要相信 session JSON 里的聚合状态；trace 又只是单次 run 的审计。

DeepSeek 的强规则是：**模型可见即已记录**。任何进入模型请求的内容，都应该可以从 session log 重建。Alibaba OCR 也用 JSONL 记录 request/response/tool/item/session。

RepoPilot 如果有事件日志，就能把恢复、回放、审计统一起来。

### 改完有什么好处

1. **恢复更可靠**  
   不依赖一份可能被部分写坏的聚合 JSON。

2. **调试更清楚**  
   可以逐事件复盘：模型看到了什么，调用了什么工具，结果是什么。

3. **为 fork/replay/snapshot 做基础**  
   以后想做 replay benchmark 或 session viewer，会容易很多。

4. **面试更有深度**  
   你能讲 event sourcing、projection、replay invariant。

### 需要改哪些代码

主要涉及：

- `repopilot/session_store.py`
- `repopilot/run_store.py`
- `repopilot/runtime.py`
- `repopilot/agent_loop.py`
- `repopilot/checkpoint.py`
- `repopilot/features/memory.py`
- `tests/test_session_store.py`
- `tests/test_checkpoint.py`
- `tests/test_agent_loop.py`

建议新增：

- `repopilot/session_events.py`
- `repopilot/session_projection.py`
- `tests/test_session_events.py`
- `tests/test_session_projection.py`

### 具体怎么改

第一步：定义事件类型。

```python
SESSION_EVENT_SCHEMA_VERSION = 1

@dataclass(frozen=True)
class SessionEvent:
    seq: int
    type: str
    created_at: str
    data: dict
```

事件类型可以先支持：

- `session_started`
- `user_message`
- `assistant_message`
- `tool_call`
- `tool_result`
- `checkpoint_created`
- `memory_note_added`
- `memory_promoted`
- `session_ended`

第二步：新增 JSONL writer。

路径可以是：

```text
.repopilot/sessions/<session_id>.events.jsonl
```

第三步：在 `AgentLoop.run()` 关键位置写事件。

例如用户输入进来：

```python
agent.session_events.append("user_message", {"content": user_message})
```

工具执行前：

```python
agent.session_events.append("tool_call", {"name": name, "args": args})
```

工具执行后：

```python
agent.session_events.append("tool_result", tool_result.to_dict())
```

第四步：写 projection。

从 events 生成当前 `session["history"]`：

```python
history = project_history(events)
```

先保留旧 session JSON，避免一次改动太大。event log 可以作为新权威来源逐步替换旧字段。

### 怎么测试

新增测试：

- 多工具 run 可以从 events 重建 history。
- 中断 session 只 replay 已完整写入事件。
- corrupted optional event 可以跳过或标记 warning。
- corrupted required event fail closed。
- prompt 中的 history 和 projection 一致。

可量化指标：

- replay success rate。
- resume correctness。
- prompt/history mismatch count。
- corrupted event detection count。

### 面试怎么说

> 我引入 append-only session event log，把用户消息、工具调用、工具结果、checkpoint 和 memory 变化都记录为事件，再通过 projection 生成模型历史和报告。这样模型可见内容可以回放，恢复不依赖脆弱的聚合状态，也让 trace、resume 和 benchmark 有统一事实来源。

## P3：轻量规则系统

> 是按语言/路径/任务动态选规则，而不是所有场景都塞同一份 README。

### 专业术语

**Rule System（规则系统）**  
把项目约定、语言约定、文件类型约定按路径匹配后注入 prompt。

**Path-based Rule（基于路径的规则）**  
不同文件匹配不同规则。例如：

```json
{
  "rules": [
    {
      "path": "**/*.py",
      "rule": "Prefer pytest-style tests and keep functions small."
    },
    {
      "path": "**/security*.py",
      "rule": "Pay special attention to path traversal and secret leakage."
    }
  ]
}
```

**Include/Exclude**  
决定哪些文件应该纳入任务，哪些文件应该跳过。

### 为什么要改

RepoPilot 当前主要靠 workspace docs、README、memory 和 prompt prefix 给模型上下文。问题是：

- 不同文件类型的规则混在一起。
- 模型可能看了很多无关约定。
- 项目规则是否命中不可测试。

Alibaba OCR 在这方面做得很好：它通过路径匹配决定每个文件应使用哪条 review rule。这让 prompt 更聚焦。

### 改完有什么好处

1. **减少 prompt 噪声**  
   只注入当前文件/任务相关规则。

2. **行为更可预测**  
   哪条规则生效可以测试。

3. **更适合多语言仓库**  
   Python、Go、JS、YAML 可以有不同规则。

4. **简历亮点明确**  
   “path-based rule resolver” 比“读 README”更工程化。

### 需要改哪些代码

主要涉及：

- `repopilot/context_manager.py`
- `repopilot/prompt_prefix.py`
- `repopilot/workspace.py`
- `repopilot/tools.py`
- `tests/test_context_manager.py`

建议新增：

- `repopilot/rules.py`
- `tests/test_rules.py`
- `.repopilot/rules.json` fixture。

### 具体怎么改

第一步：定义规则文件。

```json
{
  "include": ["repopilot/**/*.py", "tests/**/*.py"],
  "exclude": ["**/__pycache__/**", "**/*.generated.py"],
  "rules": [
    {
      "path": "tests/**/*.py",
      "rule": "Tests should use FakeModelClient and avoid network."
    },
    {
      "path": "repopilot/**/*.py",
      "rule": "Runtime code should keep dependencies minimal."
    }
  ]
}
```

第二步：实现 resolver。

```python
class RuleResolver:
    def match(self, path: str) -> RuleMatch:
        ...
```

第三步：在工具读取/搜索文件后，记录 recent files；`ContextManager` 根据 recent files 或当前任务候选文件注入 matched rules。

第四步：prompt metadata 记录：

```json
{
  "matched_rules": [
    {"path": "repopilot/runtime.py", "pattern": "repopilot/**/*.py"}
  ]
}
```

### 怎么测试

新增测试：

- `tests/**/*.py` 匹配 test rule。
- exclude 优先级高于 include。
- 无规则时回退为空。
- prompt metadata 包含 matched rule。

可量化指标：

- rule match accuracy。
- prompt rule chars reduction。
- irrelevant rule count。

### 面试怎么说

> 我借鉴 OpenCodeReview 的 path-based rules，在 RepoPilot 中引入轻量规则解析器。它按文件路径匹配项目约定，只把相关规则注入 prompt，并在 metadata 中记录命中情况。这样减少上下文噪声，也让项目规则是否生效可以单元测试。

## P4：Coverage Manifest

### 专业术语

**Coverage Manifest（覆盖率清单）**  
结构化记录一次 agent run 到底覆盖了哪些文件，哪些读过、哪些改过、哪些验证过、哪些失败。

它不是测试覆盖率，而是 agent 任务覆盖率。

例如：

```json
{
  "terminal_state": "complete",
  "coverage": {
    "planned": ["a.py", "b.py"],
    "inspected": ["a.py", "b.py"],
    "modified": ["a.py"],
    "verified": ["a.py"],
    "failed": []
  }
}
```

**Terminal State（终态）**  
任务最终状态，例如：

- `complete`
- `partial`
- `failed`
- `skipped`

### 为什么要改

RepoPilot 现在 report 里有 attempts、tool_steps、final_answer、prompt_metadata 等，但缺少一个问题的答案：

> 这次任务到底覆盖了哪些文件？哪些修改被验证了？

Alibaba OCR 的 manifest 很强：它记录 selected、completed、reused、failed、waived。这样可以证明 review 覆盖率。

RepoPilot 做通用 coding agent，不一定要照搬 review coverage，但可以做任务级 coverage manifest。

### 改完有什么好处

1. **agent 行为更可审计**  
   不只是“Done”，而是能看到它读了什么、改了什么、验证了什么。

2. **更适合简历数据**  
   可以统计 file coverage rate、verification rate。

3. **防止假完成**  
   如果改了文件但没运行验证，manifest 能暴露。

4. **支持 resume 数据**  
   可以记录 reused/rerun/invalidated。

### 需要改哪些代码

主要涉及：

- `repopilot/task_state.py`
- `repopilot/run_store.py`
- `repopilot/runtime.py`
- `repopilot/tool_executor.py`
- `repopilot/evaluation/metrics.py`
- `tests/test_task_state.py`
- `tests/test_run_store.py`
- `tests/test_metrics.py`

建议新增：

- `repopilot/coverage_manifest.py`
- `tests/test_coverage_manifest.py`

### 具体怎么改

第一步：定义 manifest。

```python
@dataclass
class CoverageManifest:
    planned_files: list[str]
    inspected_files: list[str]
    modified_files: list[str]
    verified_files: list[str]
    failed_files: list[dict]
    skipped_files: list[dict]
    terminal_state: str
```

第二步：工具执行时更新覆盖状态。

- `read_file`：加入 `inspected_files`。
- `search`：可以记录 search scope。
- `write_file` / `patch_file`：加入 `modified_files`。
- `run_shell`：
  - 如果命令像 `pytest`、`ruff`、`mvn test`，可以记录 `verified_files` 或 `verification_commands`。
  - 失败时记录 failure classification。

第三步：`report.json` 增加：

```json
{
  "coverage_manifest": {...}
}
```

第四步：metrics 聚合 coverage。

### 怎么测试

新增测试：

- 读文件会进入 inspected。
- patch 文件会进入 modified。
- run tests 成功会进入 verification。
- 工具失败会进入 failed classification。
- terminal_state 根据 coverage 计算。

可量化指标：

- file coverage rate = inspected / planned。
- verification rate = verified / modified。
- failed count by reason。
- skipped count by reason。

### 面试怎么说

> 我参考 OpenCodeReview 的 run manifest，在 RepoPilot 中设计 coverage manifest。它记录 planned、inspected、modified、verified、failed 文件集合，让一次 agent run 不只是自然语言结果，而是有可审计的结构化覆盖率。这样可以量化 agent 是否真的检查了关键文件、是否验证了修改。

## P5：Review/Inspect 专用模式

### 专业术语

**Vertical Agent Mode（垂直任务模式）**  
不是让 agent 自由做任何事，而是针对一个具体任务类型设计确定性流程。比如 code review、test fixing、dependency audit。

**Per-file Subtask（按文件子任务）**  
把大任务拆成多个文件级小任务，每个任务上下文更小、更稳定。

**Structured Finding（结构化发现）**  
问题输出不是一段文字，而是结构化对象：

```json
{
  "path": "src/a.py",
  "line": 42,
  "severity": "high",
  "category": "bug",
  "snippet": "x = user_input",
  "rationale": "...",
  "suggestion": "..."
}
```

### 为什么要改

RepoPilot 是通用 coding agent，但通用 agent 在大仓库任务上容易出现：

- 文件看不全。
- 搜索路径不稳定。
- 输出难评估。
- 大变更 token 成本高。

Alibaba OCR 的关键经验是：对 code review 这种任务，外层流程要确定性控制，模型只做语义判断。

RepoPilot 可以新增一个轻量 `inspect/review` 模式，不改变主定位，但增加一个垂直能力。

### 改完有什么好处

1. **大变更更稳定**  
   先确定文件集合，再逐个分析。

2. **输出可评估**  
   structured finding 可以算 precision、anchored rate。

3. **面试亮点强**  
   能讲“通用 harness + 垂直模式”的设计。

4. **更容易和 Alibaba OCR 对比**  
   你不是复制 OCR，而是把它的 deterministic pipeline 思想用于 RepoPilot。

### 需要改哪些代码

主要涉及：

- `repopilot/cli.py`
- `repopilot/runtime.py`
- `repopilot/tools.py`
- `repopilot/context_manager.py`
- `repopilot/evaluation/evaluator.py`

建议新增：

- `repopilot/inspection.py`
- `repopilot/findings.py`
- `tests/test_inspection.py`
- `tests/test_findings.py`
- `benchmarks/inspection_tasks.json`

### 具体怎么改

第一步：定义 finding schema。

```python
@dataclass
class Finding:
    path: str
    line: int
    severity: str
    category: str
    snippet: str
    rationale: str
    suggestion: str
```

第二步：新增 inspect prompt。

要求模型只能输出：

```xml
<finding>{...}</finding>
```

或调用：

```xml
<tool>{"name":"read_file",...}</tool>
```

第三步：确定性文件选择。

可以先支持：

- 当前 git diff 文件。
- 用户传入 path。
- search 命中的文件。

第四步：每个文件单独运行 bounded read-only loop。

第五步：汇总 findings，写入 report 和 coverage manifest。

### 怎么测试

新增 benchmark：

- fixture 里埋已知 bug。
- 模型脚本输出 finding。
- 验证 path/snippet/line 是否正确。
- 对比没有 inspect mode 时工具调用次数和 prompt 长度。

可量化指标：

- finding pass rate。
- anchored finding rate。
- exact line match rate。
- token per file。
- avg tool calls per file。

### 面试怎么说

> RepoPilot 本身是通用 coding agent，但我额外设计了一个 review/inspect 垂直模式。它先用确定性逻辑选择文件，再按文件运行 bounded read-only subtask，输出 structured finding。这样借鉴了 OpenCodeReview 的 per-file pipeline，但保留 RepoPilot 的轻量通用 harness 定位。

## P6：上下文压缩实验

### 专业术语

**Context Window（上下文窗口）**  
模型一次请求能看到的 token 上限。

**Context Compression（上下文压缩）**  
当历史太长时，把旧历史摘要成更短内容，保留关键信息。

**Section Clipping（分段裁剪）**  
RepoPilot 当前方式：prefix、memory、history 等 section 各有预算，超了就按规则裁剪。

**Three-zone Compression（三分区压缩）**  
Alibaba OCR 的方式：

- frozen：最重要的开头消息，不动。
- compress：中间旧历史，摘要。
- active：最近工具轮次，原样保留。

**Ablation（消融实验）**  
关闭或替换某个模块，对比指标变化，用来证明这个模块是否有效。

### 为什么要改

RepoPilot 已经有 `ContextManager`，能做预算控制。但面试官可能会问：

> 你的 memory/context reduction 真的有效吗？

P6 的目的不是一定替换当前策略，而是做实验：

- 当前 section clipping 效果如何？
- 三分区 tool-round compression 是否更好？
- memory 是否减少重复读文件？
- 压缩是否降低 token 且不损失任务通过率？

这会让你的项目从“我实现了 memory”变成“我用实验验证 memory 策略有效”。

### 改完有什么好处

1. **能产出数据**  
   token reduction、pass rate、repeated read count。

2. **能解释取舍**  
   不是盲目说压缩好，而是能说明何时 section clipping 更简单，何时三分区更好。

3. **简历更可信**  
   有 ablation benchmark，比纯功能描述更有说服力。

### 需要改哪些代码

主要涉及：

- `repopilot/context_manager.py`
- `repopilot/features/memory.py`
- `repopilot/evaluation/metrics.py`
- `scripts/run_large_scale_experiments.py`
- `tests/test_context_manager.py`
- `tests/test_memory.py`

建议新增：

- `repopilot/context_compression.py`
- `tests/test_context_compression.py`
- `scripts/run_context_compression_experiment.py`

### 具体怎么改

第一步：定义 tool round。

一轮可以是：

- assistant tool call。
- tool result。

RepoPilot 当前 history item 里有 role/tool/name/args/content，可以从中分组。

第二步：实现三分区。

```python
frozen = first_user_request_and_prefix
active = last_k_tool_rounds_that_fit_budget
compress = older_rounds
```

第三步：压缩 compress 区。

轻量阶段可以不用真实 LLM 压缩，先用 deterministic summarizer：

- 保留工具名。
- 保留文件路径。
- 保留错误状态。
- 保留 diff summary。

后续再加 FakeModel/真实模型压缩。

第四步：加 feature flag：

```python
context_strategy = "section_clipping" | "tool_round_compression"
```

第五步：metrics 对比两个策略。

### 怎么测试

新增测试：

- 最近 tool result 不会被压缩掉。
- 当前用户请求永远保留。
- 压缩后 prompt 低于预算。
- 文件路径和失败工具状态仍保留。

实验指标：

- prompt chars/tokens。
- retained active rounds。
- repeated reads。
- task pass rate。
- compression failure count。

### 面试怎么说

> 我没有只停留在“加了上下文裁剪”，而是设计了 context compression ablation。RepoPilot 原本使用 section-based budget clipping，我又参考 OpenCodeReview 的 frozen/compress/active 三分区策略做实验，对比 prompt token、任务通过率和重复读取次数，用数据判断哪种策略更适合轻量 coding agent。

## P1-P6 的依赖关系

建议顺序不要乱：

1. **P1 先做**：没有 structured tool result，后面的 event log、manifest、metrics 都缺少稳定字段。
2. **P2 第二**：event log 是 replay、resume、snapshot 的基础。
3. **P3 可以并行**：规则系统独立，但会影响 prompt。
4. **P4 依赖 P1/P2**：manifest 最好从结构化工具结果和事件里生成。
5. **P5 依赖 P3/P4**：inspect mode 需要规则和 coverage。
6. **P6 可以在 P2 后做**：压缩实验需要稳定 transcript 和 metrics。

## 面试总回答

如果面试官问“你这个项目后续怎么从 demo 变成更工程化的 agent harness”，可以这样说：

> 我把改造分成六步。第一步先把工具协议结构化，解决文本解析脆弱的问题。第二步引入 append-only session event log，让模型可见历史可以回放。第三步加 path-based rule resolver，减少无关 prompt 噪声。第四步做 coverage manifest，把 agent 读了什么、改了什么、验证了什么变成可审计数据。第五步借鉴 OpenCodeReview 做一个 review/inspect 垂直模式，用确定性文件选择和 structured finding 提升大变更分析稳定性。第六步做上下文压缩 ablation，用 token、通过率、重复读取次数证明 memory/context 策略是否有效。这样 RepoPilot 不是简单调用 LLM，而是在实现一个轻量但完整的 agent runtime。
